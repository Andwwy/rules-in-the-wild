# Tested toolboxes, not retrieval, fix enforcement translation

Yes, better context will help arm C, but RAG over tool documents is the wrong form. The best fit for this pipeline is a fixed lookup keyed by the Jev route. The lookup loads three short "route cards" (one per leaf) on top of a shared, pre-tested enforcement toolbox. The agent must then pass a must-flag and must-pass fixture test before it stops. The task-46 failures are mostly not missing facts. They are wiring errors (hook exit code and JSON contract), expressiveness errors (Semgrep cannot compute a name length), and coverage errors (arrow functions, files made by shell commands, an over-broad "code file" list). Papers from 2025–2026 remove these error classes with a fixed engine, typed slots and an executable test, not with more documents. With a validator loop and tools, QLCoder lifts Claude Code from **10% to 55%** correct CodeQL queries. Structured decomposition lifts Rego correctness from **15.3% to 50.3%**. In SkillsBench, curated skills lift Claude Code with Haiku 4.5 from **11.0% to 27.7%**, but skills that the agent writes for itself give **11.0%**, which is no gain. A graph helps only as a small set of hand-made "requires" edges that force coverage. It does not help as GraphRAG. For a fair test, give the toolbox, the hook contract and the test step to both B and C, so that C differs only by the route and its cards. Add a wrong-route control and a search-the-catalog control. Score with hidden fixtures and with a harness that runs outside the agent. Use many tasks and repeats, because a 3-of-70 gap on one task is noise.

## Task 46 shows three error classes that more documents do not fix

The arm-B and arm-C failures fall into classes that the literature already names. The first class is wiring. Claude Code blocks an action only on exit code 2. Any other non-zero code is a non-blocking error, and the action continues. On `PreToolUse`, the documented deny field is `hookSpecificOutput.permissionDecision: "deny"`. Top-level `decision: "block"` is documented for other events, such as `Stop` and `PostToolUse` ([Hooks reference](https://code.claude.com/docs/en/hooks)). Thus arm B's "exit 1 plus a JSON block decision" could never block. Codex CLI still accepts the legacy `{"decision":"block"}` shape ([Codex hooks docs](https://learn.chatgpt.com/docs/hooks)). That is a near-miss fact from a neighbor tool, and near-miss facts mislead models most (see the next section). Made-up event names and an invalid schema make Claude Code drop the hook with no error. None of these errors is about the rule itself. They are errors in the engine layer. The policy-enforcement systems in this review keep that layer fixed and out of the LLM's hands. AgentSpec, ToolGuard, FORGE and PolicyGuide all do this. Anthropic's own `hookify` plugin does the same: the user writes a pattern, and a fixed engine handles events, exit codes and the block-or-warn action ([hookify](https://github.com/anthropics/claude-code/tree/main/plugins/hookify)).

The second class is expressiveness. Semgrep's `metavariable-comparison` supports arithmetic, comparisons, `int()`, `str()` and `re.match()`. It documents no `len()`, no user functions and no loops ([Semgrep rule syntax](https://docs.semgrep.dev/writing-rules/rule-syntax)). So no Semgrep rule can check "class-name length is prime." The route named Semgrep, the agent installed it, and then the agent fell back to improvised scripts. The arm-C note told the agent what Semgrep is. It did not tell the agent what Semgrep cannot do, or which tool to use instead.

The third class is coverage. The function-name regex missed JS arrow functions and methods (R6: 0/10 in C). The file-name rule checked only `Write` and `Edit` calls, so files made by shell commands escaped (R8: 0/10 in every arm). The "code file" list included `.json`, `.yaml` and `.html`. LLM-written checkers fail this way in other domains too. AgentSpec's o1-written rules overfit to the given examples and missed unlisted sensitive files ([AgentSpec](https://arxiv.org/html/2503.18666v3)). Rule synthesis from one before-and-after pair fails mainly by over- and under-generalization ([Allain et al.](https://arxiv.org/html/2609.03592)). Autogrep removed **71%** of its patch-validated Semgrep rules as overly specific ([Autogrep](https://securityboulevard.com/2025/02/autogrep-automated-generation-and-filtering-of-semgrep-rules-from-vulnerability-patches/)).

Two more facts complete the picture. The eight ad-hoc scripts, each with its own copy of the extension list, are self-written skills. SkillsBench measured **zero gain** for Haiku 4.5 from self-written skills ([SkillsBench v1](https://arxiv.org/html/2602.12670v1)). The unused Semgrep venv matches the most common setup failure: an install that is incomplete or not tied to use. In SetupX, incomplete installs cause about **38%** of failures, and a venv that is not on `PATH` is a named failure mode ([SetupX](https://arxiv.org/html/2605.26186)). In ToolMaker's tests, nearly half of a general agent's environment scripts crashed at install time. The causes were untested scripts, missed setup commands and missing dependencies ([ToolMaker](https://arxiv.org/html/2502.11705v2)).

| Task-46 failure | Error class | What removes it | Evidence |
|---|---|---|---|
| B: exit 1 + JSON block; made-up events; bad schema | Wiring | A fixed runner owns events, exit 2 and JSON; a harness checks liveness | [Hooks reference](https://code.claude.com/docs/en/hooks), [hookify](https://github.com/anthropics/claude-code/tree/main/plugins/hookify) |
| C: Semgrep rule `^[A-Z].*$` for "prime length" | Expressiveness | Card lists what the tool cannot express and names the fallback adapter | [Semgrep rule syntax](https://docs.semgrep.dev/writing-rules/rule-syntax) |
| R6: arrow functions and methods missed | Coverage (syntax forms) | Toolbox owns the node-kind list per language; fixtures cover each form | [KNighter](https://arxiv.org/html/2503.09002v3) |
| R8: shell-made files missed | Coverage (trigger) | Trigger card requires a `Bash` and `Stop` check, not only `Write`/`Edit` | [Hooks reference](https://code.claude.com/docs/en/hooks) |
| `.json`, `.yaml`, `.html` treated as code | Coverage (target scope) | A fixed extension set in the toolbox; must-pass trap fixtures | [AgentSpec](https://arxiv.org/html/2503.18666v3) |
| 8 scripts with duplicated lists | Self-written tooling | Shared adapters, written and tested once | [SkillsBench v1](https://arxiv.org/html/2602.12670v1) |
| Semgrep venv installed, not used | Install not tied to use | One recipe: pinned install, then a smoke test on a bad fixture | [ToolMaker](https://arxiv.org/html/2502.11705v2), [SetupX](https://arxiv.org/html/2605.26186) |

## Retrieval helps with rare facts and hurts with near misses

Document retrieval pays off when the API is rare or new and the model is weak. For common tools it adds little, and it can hurt. In CodeRAG-Bench, gold documents moved GPT-4o from **52.7 to 51.2** on DS-1000. On the rare-library split, they moved it from **20.7 to 27.6** ([CodeRAG-Bench](https://arxiv.org/html/2406.14497)). In CloudAPIBench, document augmentation raised valid low-frequency API calls from 38.58% to 47.94%. With weaker retrievers, it also cut high-frequency accuracy by **39.02 points**. Retrieval that ran only when needed gave +8.20 points ([CloudAPIBench](https://arxiv.org/pdf/2407.09726)). Semgrep, ESLint, Ruff, git hooks and file permissions are high-frequency tools. The rare and version-sensitive facts in this pipeline are few: the Claude Code hook contract, ESLint flat config versus legacy `.eslintrc`, and Semgrep rule-schema details.

The case for retrieval is real for rare query languages. In QLCoder's ablation, removing document retrieval dropped CodeQL success from 55% to 20% ([QLCoder](https://arxiv.org/html/2511.08462v4)). CodeQL is a rare language. The same ablation shows that the language server was worth almost as much (55% to 25% without it). So the lesson is not "no documents." The lesson is that the few rare facts belong in a curated card or in the toolbox, not in a search over a large corpus.

Near-miss content is the main risk. Jin et al. found that "hard negatives" (passages that look relevant but lack the answer) make quality fall as more passages arrive. A stronger retriever found harder negatives and made the fall steeper ([Jin et al.](https://arxiv.org/abs/2410.05983v1)). Chroma's context-rot tests on 18 models found that accuracy falls as input grows, and that a single distractor already lowers accuracy ([Chroma](https://research.trychroma.com/context-rot)). For this pipeline, the legacy `decision: "block"` shape and the `.eslintrc` pages are textbook hard negatives. A curated store must exclude them, not rank them lower.

On-demand document tools also go unused. In Margin Labs' Terminal-Bench test, Codex called Context7 in only **6 of 89** tasks, and the score moved from 70.8% to 71.9%, which is noise ([Margin Labs](https://marginlab.ai/blog/do-mcps-improve-coding-agents-part-1/)). Vercel found that an 8 KB docs index placed in AGENTS.md reached **100%**, while skills peaked at **79%**, and the agent did not invoke the skill in 56% of cases ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). The docs URL in the current arm-C note is an on-demand pointer of this kind. Execution feedback also beats retrieval. In GitChameleon 2.0, RAG gave Claude 3.7 Sonnet +7.3 points (48.8 to 56.1), but self-debugging with error feedback gave about +10 to +20 points across models ([GitChameleon 2.0](https://arxiv.org/html/2507.12367)).

The framing "precision of information" fits the evidence with one change. RAGAS "context precision" is a ranking metric: it rewards relevant chunks at the top ([RAGAS](https://docs.ragas.io/en/latest/concepts/metrics/context_precision.html)). Google's Sufficient Context work argues that the right target is sufficiency, not relevance ([Sufficient Context](https://arxiv.org/pdf/2411.06037.pdf)). So a precise card holds everything the route needs and nothing that misleads. The Jev route also removes the need for a retriever. The route is already a fixed key into a hierarchy, so a lookup table returns the right card with zero retrieval error. RAG-MCP showed the value of this kind of selection: loading only the matching tool schema raised tool-selection accuracy from **13.62% to 43.13%** ([RAG-MCP](https://arxiv.org/html/2505.03275v1)). The route gives that selection with no embedding, no reranker and no index to keep current.

## A graph earns its place as coverage edges, not as GraphRAG

General GraphRAG is a poor fit here. GraphRAG-Bench reports that GraphRAG often does worse than plain RAG on simple fact lookups and pays off only on complex, hierarchical reasoning ([GraphRAG-Bench](https://arxiv.org/html/2506.05690v3)). A route-to-card lookup is the simplest lookup there is. An LLM-built entity graph over tool documents would add cost and new errors.

A small, hand-made graph does pay off when the needed item links to the query by structure and not by text. Graph RAG-Tool Fusion follows "prerequisite" edges in a tool graph and gains **+71.7 and +22.1 points** of mAP@10 over plain RAG ([Graph RAG-Tool Fusion](https://arxiv.org/abs/2502.07223v1)). Tool Graph Retriever starts from the same observation: prerequisite tools often share no words with the request, so similarity search misses them ([Tool Graph Retriever](https://arxiv.org/html/2508.05152v1)). R8 is exactly this case. "File name has odd length" says nothing about `Bash`, yet full coverage needs a check on files that shell commands make. PolicyGuide shows the same effect for workflows: a compiled policy graph scored **0.675** on its telecom test split, against **0.350** for the same system with raw policy text ([PolicyGuide](https://arxiv.org/html/2608.19861v1)). AgentSkillOS reports that a DAG of skills does much better than flat use of the identical skill set ([AgentSkillOS](https://arxiv.org/abs/2603.02176)).

So the "graph of concrete actions keyed by the Jev route" is a good idea if it has two properties. First, the nodes hold executable atoms, not prose. SetupX gives a tested template for such a node: match signals, short advice, executable steps and success telemetry. With these units SetupX reached **92%** setup success, against 82% without them ([SetupX](https://arxiv.org/html/2605.26186)). Second, the edges are few and typed. Four edge types cover the task-46 failures. An `implemented_by` edge maps each of the 103 enforcer leaves to one of a few adapters. A `cannot_express` edge marks predicate classes that a tool cannot check, with a fallback adapter. A `requires` edge adds a coverage obligation. A `verified_by` edge links a leaf to its fixture recipe. For example, the trigger leaf for file writes `requires` a `PreToolUse` check on `Write|Edit|MultiEdit`, a `PostToolUse` check on `Bash`, and a `Stop` hook that scans the workspace and exits 2. The `Stop` hook matters because a `PostToolUse` hook reports only after the tool already ran, while `Stop` with exit 2 stops Claude from finishing ([Hooks reference](https://code.claude.com/docs/en/hooks)). The target leaf for JS function names `requires` function declarations, arrow functions bound to names, class methods and object methods. The Semgrep enforcer leaf `cannot_express` length, parity or primality of an identifier, and it falls back to the AST-script adapter. A graph of about 212 leaves with these edges is small enough to write and review by hand.

## The winning shape is a fixed engine, typed slots and an executable test

The strongest systems in this review share one shape. A fixed, tested engine does the hard, general work. The LLM fills small typed slots. An executable test accepts or rejects the result. ToolGuard builds a deterministic skeleton with empty guard stubs, and the LLM fills the stubs by test-driven development. It reached pass^10 **0.500**, against **0.273** for reflection with the policy document in context ([ToolGuard](https://arxiv.org/html/2507.16459v1)). KNighter gives the LLM a checker template, 9 documented utility functions and 3 hand-built examples. Examples selected by RAG gave the same 12 valid checkers at about twice the token cost ([KNighter](https://arxiv.org/html/2503.09002v3)). IRIS keeps the CodeQL query fixed and lets the LLM supply only taint specifications ([IRIS](https://proceedings.iclr.cc/paper_files/paper/2025/hash/582d4e27fa24168f3af1f4582655034b-Abstract-Conference.html)). LintCFG compiles coding standards through a DSL into linter configs and more than doubles precision over baselines ([LintCFG](https://arxiv.org/abs/2602.07783)). In GuardAgent, removing the toolbox functions dropped accuracy from 98.7 to 90.8 ([GuardAgent](https://arxiv.org/html/2406.09187)). MTAC-IFBench itself uses this shape for its own checkers: each objective constraint becomes a small Python function built on shared helpers ([MTAC-IFBench](https://arxiv.org/html/2609.14992v1)).

The skill literature points the same way, and it adds a warning about prose. In SkillsBench, one focused skill gave **+17.8 points** and 2–3 skills gave +18.6, but 4 or more gave only +5.9. "Comprehensive" skills scored **−2.9** ([SkillsBench v1](https://arxiv.org/html/2602.12670v1)). A controlled follow-up rewrote skills at high, medium and low abstraction, with and without a worked example, and found no reliable difference ([Xu and Wu](https://arxiv.org/html/2605.31408v1)). So better prose notes will not move the score much. Verified programs do. ASI's programmatic skills beat their text-skill version by **11.3%** on WebArena, and the authors credit the verification step ([ASI](https://arxiv.org/abs/2504.06821)). In SkillWeaver, APIs that strong agents built raised weaker agents by up to **54.3%** ([SkillWeaver](https://arxiv.org/abs/2504.07079)). LATM showed the same split years earlier: a strong model makes tools, and a light model uses them ([LATM](https://arxiv.org/abs/2305.17126)). The human expert's toolbox (one runner, one adapter per enforcer type, `install.sh`, tests) has exactly this shape. The right division of work is that a person or a strong model builds and tests the toolbox once, and Haiku only fills rule configs.

In practice, this changes what Session 1 produces. The agent no longer writes hook scripts. It writes one typed rule config per rule (adapter, target selector, predicate, trigger set, message), plus its own dev fixtures. A schema check rejects bad configs. The runner then writes `settings.json` and the git hooks, with exit 2 on violation, and the agent cannot get the hook contract wrong. For classification-like slots (which adapter, which trigger), JSON output works well. For slots that need reasoning, the model writes its reasoning first and fills the schema after, because strict formats hurt reasoning ([Tam et al.](https://arxiv.org/pdf/2408.02442)). Installs also become fixed recipes. `uv tool install <tool>==<version>` gives one isolated venv per tool, but its bin directory must be on `PATH` ([uv docs](https://docs.astral.sh/uv/concepts/tools/)). Tools that exist only in the agent's shell disappear for later shells, so the recipe must write `PATH` to `/etc/profile.d/` ([SetupBench](https://arxiv.org/html/2507.09063v1)). Each recipe ends with a smoke test that runs the enforcer on a known-bad fixture.

### What each route card should contain

Each rule loads three cards: one for its enforcer leaf, one for its trigger leaf and one for its target leaf. This matches SkillsBench's best range of one to three focused modules. Keep each card short, and leave out legacy formats and other tools' conventions. The table lists the fields. The current arm-C note covers part of row 6 (the pinned install) and a thin form of row 2 (one usage line). Its docs URL is an on-demand pointer that agents seldom open.

| # | Field | What it holds | Failure it prevents | Evidence |
|---|---|---|---|---|
| 1 | Adapter binding | The leaf's adapter name and its typed slot schema | Ad-hoc scripts, duplicated lists | [ToolGuard](https://arxiv.org/html/2507.16459v1), [LintCFG](https://arxiv.org/abs/2602.07783) |
| 2 | One worked example | One tested config for this leaf, chosen by route, not by text similarity | Wrong config shape | [DSL study](https://arxiv.org/html/2407.02742v1), [Gu et al.](https://arxiv.org/abs/2503.20589v1) |
| 3 | Limits | What the tool cannot express, and the fallback adapter | Semgrep for "prime length" | [Semgrep rule syntax](https://docs.semgrep.dev/writing-rules/rule-syntax) |
| 4 | Coverage obligations | The leaf's `requires` edges (syntax forms, write paths, scope) | R6, R8, `.json` as code | [Tool Graph Retriever](https://arxiv.org/html/2508.05152v1), [PolicyGuide](https://arxiv.org/html/2608.19861v1) |
| 5 | Contract facts | Only facts the runner cannot hide, stated once, with no legacy variants | Exit 1, wrong JSON field | [Hooks reference](https://code.claude.com/docs/en/hooks), [Jin et al.](https://arxiv.org/abs/2410.05983v1) |
| 6 | Install recipe | Pinned install, `PATH` persistence, smoke test | Unused or missing tool | [uv docs](https://docs.astral.sh/uv/concepts/tools/), [ToolMaker](https://arxiv.org/html/2502.11705v2) |
| 7 | Fixture recipe and acceptance | Which must-flag and must-pass cases to write, and the command that must pass | No test loop | [KNighter](https://arxiv.org/html/2503.09002v3), [QLCoder](https://arxiv.org/html/2511.08462v4) |

Two notes on these fields. On row 2, a Microsoft study of DSL generation concluded that well-chosen examples matter more than API descriptions. In the same study, API definitions retrieved by text similarity raised the rate of invented parameter names ([DSL study](https://arxiv.org/html/2407.02742v1)). On row 7, the fixture recipe must name the variants (`function`, arrow function, class method; `def`, `async def`, nested `def`) and the traps (`config.json` must pass; a file made by `echo > x.py` must be flagged). The acceptance rule follows KNighter: every must-flag case is flagged, and no must-pass case is flagged ([KNighter](https://arxiv.org/html/2503.09002v3)).

## A fair B-versus-C test shares the toolbox and hides the fixtures

The main threat to a fair test is a confound. If only C gets the toolbox, a C win measures the toolbox, not the route. The expert's 70/70 shows that a toolbox alone can carry most of the gain. So the toolbox, the runner, the toolbox README and the "run your fixtures" step must form a shared base for both B and C. C then adds only the Jev route and its three cards. This changes what B measures: B becomes "translate the rule into toolbox config with no route." To keep continuity with the current runs, also run the old no-toolbox B and C. That gives a 2×2 design (toolbox on or off, route on or off) and shows whether the route still matters once the engine is fixed.

| Arm | What the agent gets | Question it answers |
|---|---|---|
| A | CLAUDE.md only, no Session 1 | Baseline compliance and task score |
| B | Base: rule text, toolbox, README, fixture step | Can the agent enforce with no route? |
| C | Base + Jev route + 3 route cards | Value of the route and its context |
| C-search | Base + the full card catalog as files, no route | Does route selection beat agent self-search over the same content? |
| C-wrong | Base + 3 cards from a random wrong route, same length | Does card content matter, or only extra tokens? |
| Expert | Expert toolbox and hand-written config | Ceiling on the same tasks |
| B0 / C0 | Current arms, no toolbox | Continuity with existing runs |

Hold everything else fixed. Use the same model ID, the same Claude Code version, the same container image digest, the same pinned tool versions, the same prompt text outside the route block, and the same turn and time budgets. Pin the Claude Code version for a specific reason: the hook contract is the part that B got wrong, so it must be the same in every arm and every run. Record context tokens per arm, so C-wrong can show that length alone does not explain a C gain. Write the cards per leaf, before anyone looks at the evaluation tasks, and freeze them. A card written with a task's rules in view leaks rule-specific hints into C. Run C twice: once with the classifier's predicted routes (the real pipeline, with its errors) and once with gold routes (the upper bound). The gap shows how much route errors cost.

Score Session 1 with a harness that runs outside the agent. Agents overstate their own success. In Multi-Docker-Eval, Claude Sonnet 4 declared success in **47.41%** of runs but passed in **35.53%** ([Multi-Docker-Eval](https://arxiv.org/html/2512.06915v2)). The harness should check four things for each rule. First, the hook config is valid and uses real event names. Second, the hook is live: the harness sends a synthetic violating payload on stdin and expects exit 2 or a `deny`, then sends a compliant payload and expects exit 0. Third, every tool is on `PATH` in a fresh shell. Fourth, the enforcer gives the right result on a hidden fixture set. A separate step (a person, or a different model with human review) writes that hidden set, and the translating agent never sees it. This matters because "the checker passed its own tests" does not mean "the checker is correct" ([Specification study](https://arxiv.org/html/2602.13851)). AutoCedar adds human intent review for the same reason ([AutoCedar](https://www.alphaxiv.org/abs/2607.03656)). The hidden set must include the syntax variants, the scope traps and the shell-made files that broke task 46.

Score Session 2 on compliance and task performance in the same runs. Count policy checks passed out of the total, the task's function checklist, and false blocks (a hook that blocks legal work). Over-blocking is a real cost. In FORGE's AgentDojo tests, the strictest information-flow policy cut utility from 83.7% to **33.2%** ([FORGE](https://arxiv.org/html/2602.16708v4)). AgentSpec's enforcement lowered safe-task completion from 58.62% to 54.26% ([AgentSpec](https://arxiv.org/html/2503.18666v3)). A C win on compliance with a loss on the task is not a win.

Use more than one task. Task 46 gave A 43, B 42 and C 45 out of 70. One run cannot separate a 3-check gap from noise. Arm A's 61% is close to Haiku 4.5's benchmark-wide constraint success rate of **64.7%** on MTAC-IFBench, so task 46 looks typical. But the same benchmark shows compliance falls with each turn, and near-zero perfect-instance rates after about six turns for most models ([MTAC-IFBench](https://arxiv.org/html/2609.14992v1)). Use many of the 100 MTAC-IFBench instances, with at least three repeats each. Pair arms by task, treat the rule as the unit of analysis, and report bootstrap intervals. Run the expert toolbox on the same tasks, because the 70/70 result is from task 91, not task 46. Run one task first as a pilot, measure its real cost, and then decide on the full batch. Report the ceiling too. Command hooks can check only objective constraints. MTAC-IFBench checks objective constraints with scripts and subjective ones with an LLM judge ([MTAC-IFBench](https://arxiv.org/html/2609.14992v1)). Harness-IF finds that output-control and workflow rules cause **53.9%** of failures ([Harness-IF](https://arxiv.org/pdf/2608.11727)). Those rules need `Stop`-hook checks on the final state, or `prompt` and `agent` hooks, not tool-call gates.

The design also makes a testable prediction. With a shared toolbox, C's gain over B should sit in the rules where the route adds a coverage edge or an expressiveness limit, such as R6, R8 and the prime-length rule. It should be near zero on simple regex rules. If C-wrong scores like C, the cards act as general reminders, not route-specific facts. If C-search scores like C, the route's selection adds nothing beyond the content.

## Conclusion

The most precise context for a weak model is code that already ran, not text about code. Prose notes and docs URLs are the least precise form, because they make the model rebuild the engine for every rule. The evidence says to move the engine out of the model's hands, to make the route select a tested adapter and its coverage obligations, and to let the model only fill slots and pass tests. This also changes the job of the Jev route. Its value is no longer "name the right tool." Its value is "select the adapter, pull in the obligations the rule text does not mention, and choose the fixtures." That is a sharper claim, and the C-wrong and C-search controls can test it directly.

Two outcomes would both be useful. If C beats B with a shared toolbox, the route carries real information, and the classifier earns its place. If the toolbox closes most of the gap alone, enforcement translation is an engineering task that a person solves once, and the classifier only needs to route. This review found no published study that tests either outcome on coding-agent repository rules. The evidence here comes from neighbor domains: safety policies, CodeQL, Rego and web agents. The review also found no controlled study that compares CLAUDE.md-only rules with hook enforcement on the same rules. This A/B/C design, run with these controls, would fill that gap. Once the card format and the harness are fixed, GEPA-style prompt tuning against the hidden-fixture metric is a cheap next step.
