# Skill libraries, tool-making agents, and environment-setup agents: reusable verified procedures instead of prose notes

Scope note: research date 2026-10-18. Work before 2025 is marked "foundational". All numbers carry the setting in which the authors measured them. Where a source gave only a snippet or metadata, the note says so.

## Q1. Skill libraries and procedural knowledge packaging: do verified executable skills beat prose notes or RAG?

### Takeaway
Curated, focused skills give large, repeatable gains (SkillsBench: +16 pp average, and for Claude Code + Haiku 4.5 the pass rate goes from 11.0% to 27.7%). Skills that the agent writes for itself give no gain (Haiku 4.5: 11.0% to 11.0%). The best direct evidence that executable, verified skills beat text skills comes from web agents (ASI: +11.3% over a text-skill version on WebArena; the authors credit "programmatic verification" at induction time). No study in this search isolates "skill with scripts and tests" against "the same skill as prose only" on coding or tool-setup tasks.

### Cited Findings

**Foundational: Voyager (2023)**
- Voyager (Wang, Xie, Jiang, Mandlekar, Xiao, Zhu, Fan, Anandkumar; arXiv 2305.16291, May 2023, revised Oct 2023) keeps an "ever-growing skill library of executable code". It refines each program with environment feedback, execution errors and self-verification before it stores it. In Minecraft it gets 3.3x more unique items, 2.3x longer travel distance and up to 15.3x faster tech-tree milestones than the previous SOTA. The library transfers to a new world. The abstract gives no number for transfer — [arXiv 2305.16291](https://arxiv.org/abs/2305.16291)

**Anthropic Agent Skills (Oct 2025) and the open standard**
- Anthropic engineering post "Equipping agents for the real world with Agent Skills" (Barry Zhang, Keith Lazuka, Mahesh Murag; 16 Oct 2025; updated 18 Dec 2025 to announce the open standard). A skill is a directory with a SKILL.md file. It uses three levels of progressive disclosure: (1) the `name` and `description` frontmatter loads into the system prompt at startup; (2) the SKILL.md body loads when the skill looks relevant; (3) linked files load only when needed — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- The same post says that generating tokens is inefficient for some operations (its example is sorting) and that bundled code gives "deterministic reliability". In its PDF example, Claude runs a bundled script to extract form fields without loading the script or the PDF into context. The post tells authors to say clearly whether Claude must *run* a script or *read* it. The post contains no benchmark numbers — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- The post's authoring advice: start with an evaluation on representative tasks, find where the agent fails, then build skills step by step; split large SKILL.md files; the `name`/`description` drive triggering — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Spec published at agentskills.io on 18 Dec 2025. Adoption counts differ by source and date: "more than 40 adopting clients" (Sept 2026), about 40 (June 2026), 32 (March 2026). Named adopters include Claude, OpenAI Codex, GitHub Copilot, VS Code, Cursor and Gemini CLI. Sources also disagree on who stewards the spec (Agentic AI Foundation vs Anthropic via that foundation). These are secondary sources — [Atlan](https://atlan.com/know/ai-agent/ai-agent-skills/what-are-agent-skills/); [Agentman ecosystem report](https://agentman.ai/blog/agent-skills-ecosystem-report-2026)

**OpenAI Codex skills**
- Codex skills "build on the open agent skills standard". Codex first sees each skill's name, description and file path. It loads SKILL.md only when it decides to use the skill. Folder layout: required SKILL.md, optional `scripts/` (executable code), `references/` (docs), `assets/` (templates). An optional `agents/openai.yaml` sets UI metadata, invocation policy and **declares tool dependencies**. Skills are the authoring format; plugins are the install unit. Catalog: github.com/openai/skills — [OpenAI Codex docs](https://developers.openai.com/codex/skills)

**SkillsBench (Feb 2026; the main quantitative evaluation)**
- "SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks", Xiangyi Li et al. (77 authors, incl. Dawn Song), arXiv 2602.12670. v1 13 Feb 2026; v4 14 Jun 2026. v4: 87 tasks, 8 domains, curated skills plus deterministic verifiers, 18 model-harness configurations. Average pass rate 33.9% (no skills) to 50.5% (curated skills), +16.6 pp, range +4.1 to +25.7 pp. Focused skills with at most three modules beat larger bundles. Smaller models with skills can match larger models without them — [arXiv 2602.12670](https://arxiv.org/abs/2602.12670)
- v1 Table 3 (84 tasks), pass rate no skills / curated / self-generated: Claude Code + Opus 4.5 22.0 / 45.3 / 21.6; Codex + GPT-5.2 30.6 / 44.7 / 25.0; Claude Code + Opus 4.6 30.6 / 44.5 / 32.0; Claude Code + Sonnet 4.5 17.3 / 31.8 / 15.2; **Claude Code + Haiku 4.5 11.0 / 27.7 / 11.0**; Gemini CLI + Gemini 3 Flash 31.3 / 48.7 / n.a. — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)
- Self-generated skills (agent writes 1–5 skill documents into an empty skills folder, then solves the task): mean change −1.3 pp (Opus 4.5 −0.4, GPT-5.2 −5.6, Opus 4.6 +1.4, Sonnet 4.5 −2.1, Haiku 4.5 0.0). Failure rate 80.9% vs 78.4% with no skills. The authors suggest that agents spend time writing and using self-authored skills that "may contain errors or misleading guidance" (a likely cause, not a verified one) — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)
- Software engineering got the **smallest** domain gain: 38.9% with skills vs 34.4% without (+4.5 pp). Healthcare got +51.9 pp and manufacturing +41.9 pp. One SWE task (react-perf-debugging) stayed at 0% in all conditions — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)
- Skill count: 1 skill +17.8 pp; 2–3 skills +18.6 pp; 4+ skills +5.9 pp. Skill style: "Detailed" +18.8 pp, "Compact" +17.1 pp, "Standard" +10.1 pp, "Comprehensive" −2.9 pp. 16 of 84 tasks had negative deltas (worst: taxonomy-tree-merge −39.3 pp). With Codex, agents often acknowledged skill content but then implemented their own solution — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)
- Harness: Claude Code and Codex pick skills from SKILL.md frontmatter; Gemini CLI uses an explicit `activate_skill` tool. Claude Code + Opus 4.5 had the largest uplift (+23.3 pp); the authors credit native skills integration and note that Claude models "have been trained with awareness of the Agent Skills specification". High-impact skills encoded one specific workflow (e.g., an openpyxl pivot-table workflow took one task from 0% to 85.7%) — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)
- Internal number conflicts in SkillsBench v1: the abstract says +16.2 pp, the Figure 2 caption says +12.66 pp, and the self-generated mean in text (−1.3 pp) and in a table row differ. v4 changed task count and domains (86 tasks / 11 domains in v1; 87 / 8 in v4) — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1); [arXiv 2602.12670](https://arxiv.org/abs/2602.12670)
- SkillsBench does not compare "skills with scripts" against "instruction-only skills" in the text that I read (both halves of v1 checked) — [arXiv 2602.12670v1 HTML](https://arxiv.org/html/2602.12670v1)

**Follow-up SkillsBench studies (2026)**
- "Skill Availability and Presentation Granularity in LLM Agents: A Controlled SkillsBench Study" (Xiaonan Xu, Wenjing Wu; arXiv 2605.31408, 29 May 2026). 30 tasks x 5 trials. GPT-5.5: 31.3% no skill vs 67.3% original curated skill (+36.0 pp). DeepSeek V4-Flash: 26.0% vs 50.7%. Rewriting the skill at high, medium or low abstraction, with or without a worked example, gave no reliable difference (all CIs cross zero; detectable difference 8.3–16.0 pp). The original curated skills scored highest for GPT-5.5. No script-vs-prose test — [arXiv 2605.31408](https://arxiv.org/html/2605.31408v1)
- SkillLearnBench (Zhong et al.; arXiv 2604.20087, 22 Apr 2026): 20 verified skill-dependent tasks. All continual-learning skill-generation methods beat no-skill. No method wins everywhere. Stronger LLMs do not reliably write better skills. Self-feedback alone causes "recursive drift"; several iterations with external feedback give real improvement. Methods work better on tasks with clear reusable workflows — [arXiv 2604.20087](https://arxiv.org/abs/2604.20087)
- AgentSkillOS, "Organizing, Orchestrating, and Benchmarking Agent Skills at Ecosystem Scale" (Hao Li et al.; arXiv 2603.02176, 2 Mar 2026): skills go into a capability tree; tasks run as DAG pipelines of skills. Tested at 200 to 200K skills. Tree retrieval "effectively approximates" oracle skill selection. DAG orchestration "substantially outperforms" flat invocation with the identical skill set. No numbers in the abstract — [arXiv 2603.02176](https://arxiv.org/abs/2603.02176)

**Web-agent skill induction: text workflows vs programmatic skills**
- Agent Workflow Memory, AWM (Zora Zhiruo Wang, Jiayuan Mao, Daniel Fried, Graham Neubig; arXiv 2409.07429, Sept 2024; foundational for this line). It induces **natural-language** workflows from traces and gives them to the agent. +24.6% relative success on Mind2Web and +51.1% on WebArena. Online AWM's margin grows from 8.9 to 14.0 absolute points as train/test distance grows — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429)
- Agent Skill Induction, ASI, "Inducing Programmatic Skills for Agentic Tasks" (Wang, Gandhi, Neubig, Fried; arXiv 2504.06821, Apr 2025, rev. Aug 2025). Skills are **Python programs**; the agent induces, verifies and then uses them. On WebArena, ASI beats the static baseline by 23.5% and its **text-skill counterpart by 11.3%** in success rate (abstract does not say absolute or relative). Steps fall 10.7–15.3%. The authors credit the gain mainly to the "programmatic verification guarantee during the induction phase" — [arXiv 2504.06821](https://arxiv.org/abs/2504.06821)
- SkillWeaver (Boyuan Zheng et al., incl. Neubig and Yu Su; arXiv 2504.07079, Apr 2025). The agent discovers skills, practises them, and distils them into "robust APIs" (Playwright functions). +31.8% relative success on WebArena and +39.8% on real websites. APIs made by strong agents raise weaker agents by up to 54.3% on WebArena — [arXiv 2504.07079](https://arxiv.org/abs/2504.07079)
- Limits (search-result snippets only, not checked in full text): later 2026 papers report unstable learning and poor reuse for these methods on WebArena Shopping, and a sharp reuse drop for ASI, SkillWeaver and PolySkill from cross-task to cross-website to cross-domain (60-task Mind2Web subset, GPT-4.1) — [arXiv 2606.04391](https://arxiv.org/html/2606.04391v1); [arXiv 2606.17645](https://arxiv.org/html/2606.17645v1)

**Computer-use agent skill libraries**
- "Automating SKILL.md Generation for Computer-Using Agents via Interaction Trajectory Mining" (Yuexing Hao, Xiaomin Li; arXiv 2606.20363, 18 Jun 2026). Segments GUI trajectories and clusters them into candidate skills. GRPO raises skill-step accuracy only from 18.5% to 20.5%; transfer to BrowseComp+ is "essentially unchanged"; the method "underperforms trivial frequency priors" on key metrics. The authors call it a diagnostic study — [arXiv 2606.20363](https://arxiv.org/abs/2606.20363)

**Procedural memory products (Letta)**
- Letta Context-Bench "Skill Use" (7 Nov 2025) measures how well models discover and load the right skill from a library; the agent sees a skills list in memory and reads skill files with file operations. Letta implements the Agent Skills standard; agents can write skills into their own memory — [Letta blog](https://letta.com/blog/context-bench-skills); [Letta docs](https://docs.letta.com/letta-agent/skills/index.md)

**Experience units with executable parts (environment setup; see also Q3)**
- SetupX (Zihang Zhou et al., SJTU; arXiv 2605.26186, May 2026) stores each reusable item as an "eXPerience Unit" (XPU): ID, **signals** (error keywords, regex, applicability conditions such as OS and build tool), natural-language advice, **executable atoms**, and telemetry (hits, successes, failures). A retriever embeds the current state and error text, pulls top 10 from pgvector, reranks by similarity + past success rate + tier, and an LLM picks top 3. The agent trials each fix under a Docker snapshot stack and rolls back on failure. Pass rate on 100 EnvBench-derived Python repos: 92% with XPU vs 82% without. LLM reranking adds about 6–7 pp. Noisy knowledge bases hurt; plain vector retrieval suffers most — [arXiv 2605.26186](https://arxiv.org/html/2605.26186)

**Security of skills with code**
- "Agent Skills in the Wild" (Yi Liu et al.; arXiv 2601.10338, Jan 2026): 31,132 marketplace skills scanned; 26.1% have at least one vulnerability; 5.2% show high-severity patterns that suggest malicious intent. Skills that bundle executable scripts are **2.12x more likely** to have vulnerabilities than instruction-only skills — [arXiv 2601.10338](https://www.arxiv.org/abs/2601.10338)
- Follow-up "Malicious Agent Skills in the Wild" (arXiv 2602.06547): behaviourally verified 98,380 skills; confirmed 157 malicious skills with 632 vulnerabilities — [arXiv 2602.06547](https://arxiv.org/html/2602.06547v1)

### Inferences
- The user's setup (Claude Code + Haiku 4.5) is the SkillsBench row with the lowest baseline (11.0%) and a +16.7 pp gain from curated skills, but **zero** gain from self-written skills. The ad-hoc per-rule regex scripts are a form of self-generated skill. The evidence says: give Haiku a curated, tested runner; do not ask it to write one per rule.
- SkillsBench shows the smallest gain in software engineering (+4.5 pp). But its SWE tasks are bug fixes and migrations. Tool install + config + hook wiring is closer to SkillsBench's "specific workflow" tasks (e.g., the openpyxl pivot case, 0% to 85.7%), where one concrete procedure gives large gains.
- "Focused, 1–3 modules" beats "comprehensive". For a route (enforcer leaf + trigger leaf + target leaf), this argues for loading three small skills that the route selects, not one large toolbox manual. AgentSkillOS's result (DAG composition beats flat use of the same skills) supports a graph keyed by the classifier route.
- Rewording the prose of a skill (abstraction level, worked example) did not move results. What moved results was having a curated skill at all, and (in ASI) having a verified program. So effort is better spent on executable, tested parts than on better prose notes.
- The human expert's toolbox (one runner, one adapter per enforcer type, install.sh, tests) has the shape of a SkillWeaver/ASI library: verified once, reused by a weaker agent. SkillWeaver's +54.3% for weak agents using strong-agent APIs is the closest published analog to "expert builds, Haiku reuses".
- The SetupX XPU schema (signals + advice + executable atoms + telemetry) is a concrete template for a route-keyed "graph of concrete actions" node.
- Bundled scripts raise supply-chain risk in public skills (2.12x). An in-house, version-controlled toolbox avoids most of this risk.

### Gaps
- No study found that holds content constant and compares "SKILL.md with scripts + tests" vs "same SKILL.md, prose only" on coding/tool-setup tasks. ASI vs text skills (web tasks) is the closest.
- No study found that compares Agent Skills against RAG over tool documentation on the same tasks.
- Mem0 procedural memory: no primary source with numbers found in this search.
- Letta "Skill Learning" (Dec 2025): only the announcement was found; no results.
- "SKILL.nb: Selective Formalization and Gated Execution for Durable Agent Workflows" (El Hattami, Chapados, Pal; arXiv 2606.08049) looks directly relevant (formalize parts of a skill into gated executable steps), but the PDF did not extract; method and numbers not read — [arXiv 2606.08049](https://arxiv.org/pdf/2606.08049)
- Further 2026 skill benchmarks seen only as titles: SkillFlow (arXiv 2604.17308), SkillsVote (2605.18401), SkillGenBench (2605.18693), SkillEvolBench (2605.24117), AFTER procedural-memory benchmark (2606.23127), survey "Agent Skill Evaluation and Evolution" (2606.11435), survey "A Comprehensive Survey on Agent Skills" (2605.07358).
- Venues: arXiv pages for AWM, ASI and SkillWeaver list no venue; conference acceptance not verified here.

## Q2. Tool-making agents: how do they build, verify, index and reuse tools?

### Takeaway
All successful tool-makers verify a tool by executing it before they store it (unit tests on held-out inputs, environment feedback, or a success check), and they index tools by a natural-language description for later retrieval. The 2025 systems (ToolMaker, Alita-G) also capture the **install steps** as a reproducible script, and ToolMaker shows that untested install scripts are the main failure of a general agent (OpenHands: about half its environment definitions crashed).

### Cited Findings
- **LATM, "Large Language Models as Tool Makers"** (Tianle Cai, Xuezhi Wang, Tengyu Ma, Xinyun Chen, Denny Zhou; arXiv 2305.17126, May 2023; foundational). A strong LLM makes tools; a lighter LLM uses them. Tools are cached for a *class* of requests (the cache stores functionality, not answers) and reached through their APIs; a dispatcher LLM decides when a new tool is needed. GPT-4 as maker + GPT-3.5 as user gives "performance equivalent to using GPT-4 for both roles" at much lower cost (Big-Bench tasks) — [arXiv 2305.17126](https://arxiv.org/abs/2305.17126)
- **CRAFT** (Yuan et al.; ICLR 2024; foundational). GPT-4 writes code solutions for training examples; the solutions are validated and abstracted into reusable snippets that form a task-specific toolset; at inference the model retrieves snippets and runs them or conditions on them. No fine-tuning. Gains on vision-language, tabular and math tasks — [arXiv 2309.17428](https://arxiv.org/abs/2309.17428); [ICLR 2024 poster](https://iclr.cc/virtual/2024/poster/19043)
- **ToolMaker, "LLM Agents Making Agent Tools"** (Georg Wölflein, Dyke Ferber, Daniel Truhn, Ognjen Arandjelović, Jakob Nikolas Kather; arXiv 2502.11705; ACL 2025). Input: a task description, a GitHub repo URL, input arguments, and one example call — [arXiv 2502.11705](https://arxiv.org/abs/2502.11705)
  - Environment step: from a clean `python:3.12` Docker image, an agent clones the repo, reads docs and installs dependencies. ToolMaker **records every write action as a bash command**, so the output includes a reproducible environment definition (bash script or Dockerfile) — [arXiv 2502.11705v2 HTML](https://arxiv.org/html/2502.11705v2)
  - Closed loop: reset to the post-install Docker snapshot, run the candidate Python function on the example, an LLM judges output and stderr, a diagnose agent inspects failures, then re-implement — [arXiv 2502.11705v2 HTML](https://arxiv.org/html/2502.11705v2)
  - Verification (TM-Bench): 15 tasks, 2–3 held-out invocations per task, 42 invocations, 124 unit tests. A tool counts only if it passes all tests on all invocations. Result (gpt-4o): ToolMaker 12/15 tools (80%), 116/124 unit tests, $0.94 per tool; OpenHands 3/15 (20%), 31/124, $0.15. OpenHands + Claude 3.5 Sonnet: 2/15 — [arXiv 2502.11705v2 HTML](https://arxiv.org/html/2502.11705v2)
  - Failure analysis: nearly half of OpenHands' environment definitions were invalid and crashed at install time ("untested install scripts, omitted setup commands, missing dependencies"). ToolMaker failed one invocation where the test input had a feature absent from the single example — so the example must represent the task — [arXiv 2502.11705v2 HTML](https://arxiv.org/html/2502.11705v2)
- **Alita** (arXiv 2505.20286, May 2025): "minimal predefinition, maximal self-evolution". The agent generates task-related MCP servers from open-source code and reuses them. GAIA validation: 75.15% pass@1, 87.27% pass@3 (self-reported) — [arXiv 2505.20286](https://www.arxiv.org/abs/2505.20286)
- **Alita-G** (arXiv 2510.23601, Oct 2025): successful trajectories become candidate MCP tools; the system **abstracts them into parameterized primitives** and consolidates them into an "MCP Box". At inference it does retrieval-augmented MCP selection using each tool's **description and use cases**. GAIA validation: 83.03% pass@1, 89.09% pass@3, about 15% fewer tokens per example than a strong baseline (self-reported) — [arXiv 2510.23601](https://arxiv.org/html/2510.23601v1)
- Voyager (see Q1) indexes executable skills and improves them with execution errors and self-verification before storing — [arXiv 2305.16291](https://arxiv.org/abs/2305.16291)
- ASI verifies each induced program by running it before adding it to the skill set; the authors say this verification is the main source of gain — [arXiv 2504.06821](https://arxiv.org/abs/2504.06821)

| System | Unit of reuse | Verification before storing | Index / retrieval |
|---|---|---|---|
| Voyager (2023) | JS program | env feedback + errors + self-verification | description lookup (per paper; abstract does not detail) |
| LATM (2023) | Python tool for a request class | (abstract does not detail) | cache keyed by request class; dispatcher LLM |
| CRAFT (2024) | code snippet | validated on training examples | retrieval over toolset |
| ASI (2025) | Python skill (web actions) | programmatic verification at induction | skill set in action space |
| SkillWeaver (2025) | Playwright API | practice runs, then "robust API" | API library, transferable |
| ToolMaker (2025) | Python function + env script | held-out unit tests; Docker snapshot loop | per-task tool (no library) |
| Alita-G (2025) | parameterized MCP tool | from successful trajectories | RAG over description + use cases |

### Inferences
- The common pattern is: write, **run against tests in a clean snapshot**, then store with a short description used for retrieval. Prose notes skip the run-against-tests step, which every system above treats as essential.
- ToolMaker's "record every write action as a bash command" is a direct fix for the user's observed problem (agent installed a Semgrep venv but did not use it). If the install is a recorded, replayable script that ends with a smoke test of the enforcer on a sample violation, a non-used install shows up as a test failure.
- LATM's split (strong model makes, light model uses) maps onto "human expert / strong model builds the toolbox once; Haiku 4.5 only fills config and wires it". The LATM cache is keyed by a *class* of requests; the classifier route (enforcer, trigger, target) is a natural cache key.
- Alita-G's step "abstract a successful tool into a parameterized primitive" is what the expert did when one runner + one adapter per enforcer type replaced per-rule scripts (and the duplicated file-extension list).

### Gaps
- CREATOR (Qian et al., 2023): no source was fetched in this search; its numbers and verification method are not reported here.
- "Tool-Making and Self-Evolving LLM Agents in Low-Latency Systems" (arXiv 2607.08010, Jul 2026) found as a title only — [arXiv 2607.08010](https://arxiv.org/html/2607.08010v1)
- No paper found that measures tool *reuse rate* across many later tasks for coding-tool installation (as opposed to web or reasoning tasks).

## Q3. Environment-setup and installation agents: success rates, failure modes, and what scaffolding helps

### Takeaway
Unaided agents fail often at setup (EnvBench best: 6.69% Python, 29.47% JVM; Multi-Docker-Eval best fail-to-pass 37.72%; SetupBench 34–62%). The scaffolding that raises success is consistent across papers: an execute-and-check loop with a deterministic success command, snapshots and rollback, writing the final working recipe as a script/Dockerfile, reuse of earlier validated setups (memory pools, per-repo recipes, experience units), and an outside verifier because agent self-reports are unreliable. Common failures are incomplete installs, tools not on PATH in a new shell, invented constraints, and install-loop drift.

### Cited Findings

**Benchmarks**
- **SetupBench** (Avi Arora, Jinu Jang, Roshanak Zilouchian Moghaddam; arXiv 2507.09063, Jul 2025): 93 tasks from a bare Linux sandbox; each has a deterministic validation command. Categories: repo setup (54), dependency resolution (16), databases (15), background services (8). OpenHands overall success: GPT-4o 34.4%, GPT-4.1 50.5%, Claude 3.5 53.8%, Claude 3.7 57.0%, Claude 4 62.4% — [arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)
  - Failure modes: (1) installed runtime deps but not test tooling (e.g., ignored `tox.ini` → "tox: not found"), 17–26% of repo-setup failures; (2) hallucinated task constraints (changed server ports that the task never mentioned); (3) **non-persistent setup**: tools installed but missing in a fresh shell (e.g., `pnpm` not found by the harness) — [arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)
  - Waste: 38.17% (Claude 3.5 Sonnet) to 68.77% (Claude 4 Sonnet) of steps were unnecessary vs a 124-step human baseline. Patterns: repeated partial file reads, unneeded `sudo`/install checks, off-target reads — [arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)
  - Authors' recommendations: write env changes to persistent files (`.bashrc` or `/etc/profile.d/`) and source them; give structured change summaries; inject a repo tree early; require the agent to cite documentation before config changes — [arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)
- **EnvBench** (JetBrains Research; arXiv 2503.14443; ICLR 2025 DL4Code workshop): 994 repos (329 Python, 665 JVM). Python is scored by static analysis for missing imports; JVM by Gradle/Maven build. Best approach (GPT-4o / GPT-4o-mini, zero-shot and two agentic workflows): 6.69% Python, 29.47% JVM — [arXiv 2503.14443](https://arxiv.org/abs/2503.14443)
- **Multi-Docker-Eval** (Kelin Fu et al., PKU / Moonshot AI / M-A-P; arXiv 2512.06915, Dec 2025): 334 issues, 40 repos, 9 languages. Best fail-to-pass (F2P) 37.72% (SWE-Builder + DeepSeek-v3.1); Claude-Sonnet-4 35.53%. Mean across 10 models: SWE-Builder (multi-agent, repair loops, memory pool) 30.58% vs RepoLaunch (single agent, sequential bash) 8.85% — **framework matters more than model**. Self-assessment is unreliable: Claude-Sonnet-4 "commits" 47.41% of runs but passes 35.53%. Docker build errors are the largest failure class (36.09%); missing/non-executable test scripts 18.12%; silent false passes 12.70%. Go easiest (F2P 54.50%); C/C++, Java, Rust hardest — [arXiv 2512.06915v2](https://arxiv.org/html/2512.06915v2)
- **SetupX** (arXiv 2605.26186, May 2026), 100 EnvBench-derived Python repos, qwen3.5-plus, fresh ubuntu:22.04, 3600 s limit, adversarial "prosecutor–judge" verification: SetupX + experience units 92%; without experience 82%; **Claude Code 73%**; ExecutionAgent 59%; Repo2Run / EnvBench baselines 38–45% (derived from stated gaps). Swapping to Claude Opus 4.6 kept 92% at more than 10x API cost — [arXiv 2605.26186](https://arxiv.org/html/2605.26186)
  - Failure modes: stateless retry loops that switch installers and drift versions (Poetry fails → pip); non-invertible state after a failed install; missing toolchains/native libs; **incomplete installation is the most common class (about 38% of failures)**; verification mismatch (90% of EnvBench repos pass static analysis but only 38% pass when dependencies are checked in the container); PATH not linked to the venv; port collisions with leftover services; missing a Python version floor early — [arXiv 2605.26186](https://arxiv.org/html/2605.26186)

**Agents and pipelines**
- **Repo2Run** (Ruida Hu, Chao Peng, Xinchen Wang, Junjielong Xu, Cuiyun Gao; arXiv 2502.13681, Feb 2025, rev. Oct 2025): iteratively builds a Docker image, runs unit tests on build feedback, and synthesizes a Dockerfile until the pipeline works; the Dockerfile is the output. 361/420 Python repos (86.0%); "outperforming SWE-agent by 77.0%" — [arXiv 2502.13681](https://arxiv.org/abs/2502.13681). A plain LLM generator baseline got 22.1% (93 repos) — [arXiv 2502.13681 PDF](https://arxiv.org/pdf/2502.13681)
- **ExecutionAgent**, "You Name It, I Run It" (Islem Bouzenia, Michael Pradel; arXiv 2412.10133; ISSTA 2025, PACMSE 2 ISSTA047): 50 projects, 14 languages; runs the test suites of 33/50 with 7.5% deviation from ground truth; 6.6x better than the best prior technique; 74 min and USD 0.16 LLM cost per project on average — [arXiv 2412.10133](https://arxiv.org/abs/2412.10133)
- **CompileAgent** (Li Hu et al.; ACL 2025 long, pp. 2078–2091): five tools plus a flow-based strategy to find build instructions and fix errors; CompileAgentBench; compilation success +10% to +71% over two baselines. Code: github.com/Ch3nYe/AutoCompiler — [ACL Anthology 2025.acl-long.103](https://aclanthology.org/2025.acl-long.103)
- **RepoLaunch** (arXiv 2603.05026, Mar 2026; SWE-bench-Live family): about 70% build success across nine languages on Windows and Linux. A setup agent drives a live bash session until tests run, then commits the container as an image — [arXiv 2603.05026](https://arxiv.org/html/2603.05026v1)
- **SWE-Factory** (arXiv 2506.10954, Jun 2025): SWE-Builder uses four agents (search repo, write Dockerfile, install deps, write tests), a retry loop and a **memory pool that reuses validated environments** from nearby versions. v1: 269/671 valid instances across 12 repos with GPT-4.1-mini — [arXiv 2506.10954v1](https://arxiv.org/html/2506.10954v1). A later version reports 337/671 (50.2%) with GPT-4.1-mini and F2P-check precision 100% / recall 98.3% (as summarized by a survey page) — [Environment Factories](https://alpayariyak.github.io/environment-factories/). The two counts conflict across versions.
- Environment-factory survey page ("a field guide 2018 → 2026", no author named on page, latest items spring 2026): reuse patterns include one image per repo (SWE-smith), one setup run per repo with the recipe reused across tasks (SWE-rebench V2, 32,079 tasks, 20 languages), Dockerfile templates completed by an LLM with up to five retries (SWE-Bench++), and a trained builder that writes `evaluation.sh` that must fail before and pass after the fix (SWE-Universe; 94% on held-out envs after self-verification vs 82.6% before). SWE-rebench found a working recipe for at least one task in 31% of repos — [Environment Factories](https://alpayariyak.github.io/environment-factories/)

### Inferences
- The user's failures match the published taxonomy closely: "installed Semgrep venv but did not use it" = incomplete/non-persistent setup (SetupBench #3; SetupX "PATH not linked to venv"); ad-hoc per-rule scripts = stateless improvisation without reuse; hook-format mistakes = no deterministic success command that exercises the hook.
- Three scaffolding features have the strongest support across papers and are cheap to add: (a) a deterministic success command per route (SetupBench, Multi-Docker-Eval, SWE-Universe), e.g., "fire the hook on a known-bad file and expect exit code 2"; (b) a recipe that is reused, not re-derived (SWE-Factory memory pool, SWE-rebench V2, SetupX XPU 82% → 92%); (c) snapshot/rollback during trial (ToolMaker, SetupX).
- Multi-Docker-Eval's finding that the framework matters 2.5–3.5x more than the model suggests that a better scaffold will help Haiku 4.5 more than a model swap. SetupX's Opus-4.6 swap (same 92%, >10x cost) points the same way.
- Agent self-reports overstate success (47.41% claimed vs 35.53% real). The A/B/C evaluation should run its own checks, not trust the agent's "done".

### Gaps
- Installamatic: no source found in this search.
- EnvPilot (Hanwu Chen et al., incl. Daoguang Zan; arXiv 2609.07357, Sept 2026), an "experience-augmented agent for software environment setup", is directly relevant, but only PDF metadata was readable — [arXiv 2609.07357](https://arxiv.org/abs/2609.07357)
- Seen as titles only, not read: PIPer (on-device env setup via online RL, arXiv 2509.25455), EvoConfig (self-evolving multi-agent env configuration, arXiv 2601.16489), RAT: RunAnyThing (arXiv 2604.23190), DeployBench (arXiv 2606.05238), FDE-Bench (arXiv 2609.27571).
- SWE-smith: no primary source read; only the survey's one-line description ("one image per repo").
- No study found that tests Nix flakes, devcontainers or mise as the install substrate for an LLM agent versus free-form shell installs.
- No paper isolates the effect of "pinned versions" or "retrieved install docs" on success; SetupX discusses them only in case studies.

## Q4. Practical packaging: what makes "install enforcer X" deterministic?

### Takeaway
Mature tooling already turns "install tool X at version V" into one declarative line with checksums: `uv tool install ruff==V` (isolated venv per tool), mise with a lockfile (pinned versions + checksums; aqua backend verifies signatures), and Dev Container Features (versioned `install.sh` that runs as root with options as env vars). The agent then only picks from a fixed menu; it does not write install logic.

### Cited Findings
- **uv tools**: `uv tool install` makes a separate, persistent venv per tool. Pin with `uv tool install ruff==0.5.0`; add packages with `--with`; `--with-executables-from` also exposes their executables. Executables are symlinked into a bin directory that **must be on PATH** (uv warns otherwise); `uv tool update-shell` adds it to shell config. `uvx` (= `uv tool run`) runs a tool in a disposable cached env. Each tool env links to one Python; choose with `--python` — [uv docs: Tools](https://docs.astral.sh/uv/concepts/tools/)
- **mise lockfile**: `mise.lock` (marked experimental) pins exact versions and checksums; for supported backends mise stores and verifies download checksums; enable with the `lockfile` setting — [mise lock docs](https://mise.jdx.dev/dev-tools/mise-lock.html). For aqua-backend tools mise verifies Cosign/Minisign signatures, SLSA provenance and GitHub artifact attestations automatically — [mise security](https://mise.jdx.dev/security.html). v2026.10.0 made keyless cosign stricter (requires a pinned identity) — [mise v2026.10.0 release](https://newreleases.io/project/github/jdx/mise/release/v2026.10.0)
- **Dev Container Features**: a Feature is a folder with `devcontainer-feature.json` (required `id`, `version`, `name`) and `install.sh`. Each option becomes an upper-case env var for `install.sh`. `install.sh` runs as root at image build. `dependsOn` is a hard, recursive dependency (creation fails if one cannot install); `installsAfter` only orders. Features are semver-versioned and distributed as OCI artifacts (`<registry>/<namespace>/<feature>:<version>`), HTTPS tarballs or local paths. Equality is manifest digest + identical options — [containers.dev Features spec](https://containers.dev/implementors/features/)
- **Codex skills** can declare tool dependencies in `agents/openai.yaml` — [OpenAI Codex docs](https://developers.openai.com/codex/skills)
- **ToolMaker** turns an agent's install session into a reproducible bash script / Dockerfile by recording each write command — [arXiv 2502.11705v2 HTML](https://arxiv.org/html/2502.11705v2)
- **SetupBench** recommends persisting env changes in `/etc/profile.d/` or `.bashrc` and sourcing them, because tools installed only in the agent's shell vanish for the evaluator — [arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)

### Inferences
- For the user's Debian 12 container (python3, pip, wget only), a practical deterministic layer is: (1) `pip install uv` once; (2) Python-based enforcers (Semgrep, Ruff, check-jsonschema, etc.) via `uv tool install <tool>==<pin>`; (3) Node.js from a pinned official tarball checked against its published SHA-256, then ESLint etc. via `npm install -g <pkg>@<pin>`; or (4) mise with `mise.lock` for both. Each enforcer leaf then has a one-line install recipe plus a smoke test, written and tested once by a human.
- PATH persistence should be part of the recipe (write to `/etc/profile.d/enforcers.sh`), not left to the agent, because the Claude Code hook runs in a different shell from the agent's install session.
- The Dev Container Feature layout (versioned folder, `install.sh` with options as env vars, `dependsOn`) is a good on-disk format for "enforcer leaf" packages even without devcontainers: e.g., `features/semgrep/install.sh` with `VERSION` env var, and `dependsOn: node` for ESLint.
- Pinned versions also stabilise the A/B/C comparison across runs: the same rule gets the same tool version in each arm.

### Gaps
- Nix flakes / nixpkgs pins: not researched in this search (no source fetched). Nix is not present in the stated base image, so it adds an install step itself.
- asdf / aqua standalone: not fetched separately; aqua is covered only through mise's aqua backend.
- `devcontainer-lock.json` and its integrity digests: the Features spec page did not describe them.
- No evaluation found of LLM agents using any of these managers versus free-form installs.
